How It Works

Secret → Polynomial → 5 Shares → Any 3 Shares → Lagrange Interpolation → Original Secret

Shamir's Secret Sharing splits a single secret into several "shares" so that no individual share reveals anything about the secret on its own. Only when enough shares are combined (here, at least 3 out of 5) can the original secret be reconstructed.

This demo builds a random quadratic polynomial whose constant term is the secret itself. Each of the 5 shares is one point on that polynomial's curve. Because a quadratic curve is uniquely determined by exactly 3 points, any 3 shares are enough to reconstruct the whole curve — and therefore the secret hidden at its start. Any 2 points, however, could belong to infinitely many different quadratics, so 2 shares reveal nothing.

How to Operate

  1. Type a secret into the "Secret" field, or tap "Use Demo Secret."
  2. Tap "Generate 5 Shares" to split it into shares K1–K5.
  3. Tap "Copy Share" on any card to copy that single share, or "Copy All Shares" to copy all five at once.
  4. Tick the checkboxes on at least 3 share cards.
  5. Tap "Recover Secret." With 3 or more valid, non-duplicate shares, the original secret reappears. With fewer than 3, recovery is denied.
  6. Tap "Run Automatic Tests" to see the demo verify several 3-share combinations (all succeed) and insufficient-share attempts (all correctly rejected).

Mathematics

The scheme works over a finite field GF(p), where p is the well-known Mersenne prime 2⁵²¹ − 1 (the same modulus used for the NIST P-521 elliptic curve). All arithmetic — addition, multiplication, and the polynomial evaluations below — is performed modulo p, using JavaScript's BigInt type throughout so nothing is rounded or truncated by ordinary floating-point numbers.

The polynomial used is degree 2:

f(x) = a₀ + a₁x + a₂x² (mod p)

where a₀ is the secret and a₁, a₂ are random coefficients generated with crypto.getRandomValues() — a cryptographically secure random source, never Math.random().

Share i is the point (i, f(i) mod p) for i = 1 … 5. Given any 3 shares (x₁,y₁), (x₂,y₂), (x₃,y₃), Lagrange interpolation reconstructs f(0):

f(0) = Σ yᵢ · Π (0 − xⱼ)/(xᵢ − xⱼ), for j ≠ i (mod p)

A degree-2 polynomial has 3 unknown coefficients, so exactly 3 independent equations (points) are needed to solve for them uniquely — this is why the threshold is 3. With only 2 points, one degree of freedom remains unconstrained, so every possible secret value remains equally consistent with the data: this is information-theoretic security, not merely computational difficulty.

Important distinction: Shamir's Secret Sharing is a secret-sharing / threshold access-control technique. It is not encryption — it does not scramble data for confidentiality against a single party; it distributes trust so that no single party (or small group below the threshold) can act alone.

Security & Limitations

  • This is an educational, in-browser prototype for demonstration purposes only.
  • It has not undergone professional security review or penetration testing.
  • Secrets are handled entirely client-side in this demo and are never sent anywhere — but this page also has no protections against a compromised device, browser extension, or shoulder-surfing.
  • Production systems must use professionally reviewed, audited cryptographic libraries and follow secure key-management practices (secure share transport, secure storage, access logging, revocation, etc.) — none of which this demo implements.
  • Do not use real government, police, court, financial, medical, or personal data with this demo.

Future JusticeVault Architecture

This demo illustrates one building block of a proposed future architecture — it is not the production JusticeVault system, and no claim is made that any government, police department, or court currently uses this exact implementation.

Digital Evidence → AES-256 Encryption → Encrypted Evidence + AES Key → Shamir 3-of-5 protects AES Key → K1 K2 K3 K4 K5 → Any 3 Authorized Parties → Recover AES Key → Decrypt Evidence

Note the key design point: Shamir's Secret Sharing would protect the AES encryption key, not the evidence file itself. The (typically large) evidence file stays encrypted with AES-256; only the much smaller key is split into shares, so that no fewer than 3 authorized parties acting together can ever decrypt the evidence.

Proposed future components (not implemented in this demo):

  • Authentication
  • Role-Based Access Control (RBAC)
  • AES-256 encryption of evidence files
  • Shamir 3-of-5 protection of the AES key (this demo)
  • SHA-256 integrity verification
  • Digital signatures
  • Chain-of-custody tracking
  • Audit logging
  • Secure submission workflow
